# Директива 13: Сборка страниц из паттернов

> Этап 13 конвейера (00_pipeline.md). Вход: `docs/ia/wireframes/<page>.md`, `docs/ia/sitemap.md`, `docs/ds/components.md`, плагин `designstack-core` с seed-данными. Выход: `docs/ds/screens/<page>.md`, `docs/ds/screens/_index.md`, `templates/*.html`, `parts/*.html`. Запуск: /directive 13 [<page>]

## Задача

Заменить grey-box шаблоны из 08 настоящими: каждую страницу собрать как композицию паттернов из 11 и блоков из 12 по wireframe, сначала описав её в composition map (`docs/ds/screens/<page>.md`), затем — в блочной разметке `templates/*.html`. Результат — статичные, но реальные страницы с настоящими данными из seed, проверенные скриншотами в обеих темах на 1440 и 375. Логика фильтров, поиска и форм — не здесь.

## Когда применять

После 11 и 12, до 14. Режимы: **single** — `/directive 13 front-page` для одной страницы; **bulk** — без аргумента: идёт по `docs/ia/sitemap.md` по страницам с пометкой `[core]`, пропускает собранные (`_index.md`, статус `built`/`verified`), спрашивает про пересборку. Повторно — при изменении wireframe или появлении нового паттерна: пересобирает только затронутый шаблон и его карту.

## Предусловие

- `docs/ia/sitemap.md` (страница → шаблон WP) и `docs/ia/wireframes/<page>.md` — из 07/08. Нет wireframe → «`/directive 08 <page>`», не додумывать.
- `docs/ds/components.md` со статусом `built`/`verified` у нужных паттернов; витрина `/styleguide/` открывается.
- Плагин активен, `python scripts/seed.py` прогнан: `tools/wp.cmd --path=wordpress post list --post_type=resource --format=count` ≥ 24.
- Сервер поднят, `debug.log` чист на старте.

## Роль

Дизайнер-сборщик, который высаживает страницы из готовой ДС: узнаёт в wireframe паттерны каталога, не рисует с нуля, закладывает пустые и ошибочные состояния сразу, а не «потом». Фиксирует структуру в md, и только после апрува пишет разметку.

## Ключевой принцип

**Страница — композиция из базы, утверждённая текстом.** Каждая секция wireframe → паттерн из `components.md`, блок `designstack/*` или локальная композиция из тех же блоков и токенов. Нет точного совпадения — лучше локальная композиция, чем натянутый чужой паттерн. Повторилась на второй странице — кандидат на вынос, на третьей — паттерн (3+/2/1).

## Граница

- Только раскладка и статичный вид. Не подключает фильтры, поиск, пагинацию по параметрам, отправку формы, переключение состояний по действию — это 14. Блоки `designstack/*` показывают данные seed со статичными атрибутами — это нормально, это не логика.
- Не создаёт новые токены (10) и не правит CSS паттернов (11) — кроме выноса повторившейся композиции в новый паттерн через мини-цикл 11 с записью в каталог.
- Не меняет модель данных (12) и не пишет контент (16).
- Если агент начал «оживлять» (JS-обработчики, чтение `$_GET`, формы с action) — откатить, это 14.

## Фазы

### Фаза 1. Чтение и сверка

1. Прочитать `docs/ia/wireframes/<page>.md`, `docs/ia/sitemap.md` (какой шаблон WP: `front-page`, `taxonomy-resource_type`, `single-resource`, `taxonomy-topic`, `category`, `single`, `page`, `page-about`, `page-suggest`, `search`, `404`), `docs/ds/components.md`, `theme.json` (какие ширины и отступы есть), текущий grey-box шаблон в `templates/`.
2. Таблица «секция → паттерн»:

```
Секция wireframe          → Реализация
Шапка                     → parts/header.html
Hero с поиском            → search-form (variant: page) + локальная композиция (заголовок, 4 ссылки типов = badge kind:type)
«Проверено на этой неделе»→ section-header + designstack/resource-list {orderby: checked_at, limit: 6}
Свежие подборки           → section-header + core/query (category collections) + collection-item
Подписка                  → subscribe-cta (variant: block)
Подвал                    → parts/footer.html
```
Нет кандидата → `AskUserQuestion`: «Вынести паттерн через мини-цикл 11 (Recommended) / ближайший паттерн / оставить локальной композицией». Без решения не идти дальше.

3. **Анализ информационной достаточности** — шесть проверок по каждой странице, вопросы заказчику в формате `[1]…[n]`, ≤ 4 за раз, каждый с рекомендацией:
   - [1] **Сырая сущность.** Карточка в wireframe — только название? На странице раскрыть: вердикт, бейджи pricing / ru_open / ru_payment / checked_at, тип, теги.
   - [2] **Пустые зоны.** Главная и рубрики — ≥ 60 % площади первого и второго экрана заняты осмысленным контентом (списки, подборки, дайджест), не воздухом и не декором.
   - [3] **Edge cases.** Пусто / ошибка / переполнение / `dead` — есть ли в wireframe; предложить, как выглядят.
   - [4] **Уровни действий.** Кроме главного CTA есть быстрые действия (перейти к типу, к теме, подписаться, предложить ресурс)?
   - [5] **Голый текст вместо интерактива.** Мета одной строкой через «·» → бейджи с иконками; FAQ, «как проверяем», ссылки в подвале → кликабельны, с chevron или подчёркиванием.
   - [6] **Списки из одного элемента.** В шаблоне показывать реалистичное число (6–9 карточек) с разными статусами; seed это обеспечивает.

4. Повторяющиеся блоки: 3+ копии одной локальной композиции на странице или уже встречалась на другой странице (`_index.md`) → вопрос «выносим в паттерн?» с рекомендацией; «да» → мини-цикл 11 (запись в `components.md`, файл `patterns/<slug>.php`, ячейка на витрине) **до** сборки шаблона.

### Фаза 3. Лист решений

Перед разметкой собрать лист решений навыком `decision-board` — на партию страниц одного потока, не на все сразу. Три колонки: «Сейчас» — скриншот текущей страницы (grey-box из 08 или живая страница при пересборке); «Предлагаю» — схема composition map или уже собранная страница в 1440 и 375, с настоящими токенами и текстами интерфейса из `docs/VOICE.md`; «Рынок» — кадры конкурентов из `docs/research/competitors.md` с подписью, какое решение оттуда взято. Под колонками — «Решения состава» с номерами, по которым спрашивается апрув, и «Чеклист страницы». Колонка «Рынок» — кадры из `docs/research/competitive_analysis.md` (03); если 03 не прогонялся — из `docs/research/competitors.md` (02). Ответы заказчика (✔ / ✘ с причиной / ?) записываются в карточку страницы `docs/ds/screens/<page>.md` с датой и пометкой «апрув в чате»; в `docs/DECISIONS.md` уходит только итог: принятое — в «Решено», спорное — в «Открыто».

Лист публикуется инструментом `Artifact` приватной страницей; ссылка уходит заказчику и попадает в `docs/ds/screens/_index.md`. Сразу после публикации — апрув в чате через `AskUserQuestion` по навыку `decision-board`: решения без спора одним вопросом, каждое спорное — отдельным. Ответ: ✔ подходит, ✘ нет с обязательной причиной, ? непонятно. Каждый ✘ разбирается по классу: та же ошибка ищется на остальных страницах, правило со способом проверки пишется в `.claude/rules/wp-theme.md`. Принятое переносится в `docs/DECISIONS.md` (раздел «Решено», с датой), спорное — в «Открыто».

**Нет апрува — шаблон не собирается**, даже если страница кажется очевидной. Апрув — ответ заказчика в чате, записанный в карточку страницы.

### Фаза 4. Реализация шаблона

1. `templates/<template>.html` — только блочная разметка: `<!-- wp:template-part {"slug":"header"} /-->`, `<!-- wp:group {"layout":{"type":"constrained"}} -->`, `<!-- wp:pattern {"slug":"designstack/section-header"} /-->`, `<!-- wp:designstack/resource-list {"orderby":"checked_at","limit":6} /-->`, `<!-- wp:query -->` для подборок и дайджеста, `<!-- wp:post-title /-->`, `<!-- wp:post-content /-->` для single, `<!-- wp:designstack/resource-meta /-->` в `single-resource.html`, `<!-- wp:template-part {"slug":"footer"} /-->`. Grey-box шаблон перезаписывается.
2. Отступы и цвета секций — только через атрибуты блоков со ссылкой на пресеты (`"style":{"spacing":{"padding":{"top":"var:preset|spacing|12"}}}`, `"backgroundColor":"surface-subtle"`); никаких инлайн-`style` с hex/px.
3. Локальные композиции — прямо в шаблоне из core-блоков и классов паттернов (`"className":"ds-hero-links"`); стили для них — в `patterns.css` только если это уже утверждённый вынос; иначе обходиться существующими классами и утилитами.
4. Шаблон для конкретной страницы — `templates/page-<slug>.html` (`page-about.html`, `page-suggest.html`); страница создаётся WP-CLI (`post create --post_type=page --post_name=about`), шаблон назначается через `post meta update <id> _wp_page_template page-about`. Архивы типов — `templates/taxonomy-resource_type.html` (заголовок из термина, описание, место под `filter-panel`/`filter-chips` — статичные, `resource-list` по текущему термину через `core/query` или атрибут `resource_type` из query var — только чтение).
5. Тени из foundation — база, не polish: карточки `shadow-sm`, поднятые панели `shadow-md`, сразу в первом проходе. Иконки — только из `icons.svg`; нет нужной → добавить в спрайт и в список 11.
6. После каждого шаблона: `curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/<url>`, `debug.log`, `tools/wp.cmd --path=wordpress eval 'print_r( wp_get_theme("designstack")->errors() );'`.

### Фаза 5. Индекс и Used in

`docs/ds/screens/_index.md` — таблица: страница | URL | лист решений (ссылка) | шаблон | паттерны | блоки | локальные композиции | статус (`planned / built / verified`). В `components.md` у каждого задействованного паттерна — `Used in: screens/<page>` (дописать через запятую, не дублировать). Локальные композиции, встретившиеся второй раз, — пометить «кандидат на вынос: <page1>, <page2>».

### Фаза 6. Проверка и апрув

1. Скриншоты каждой собранной страницы: `python scripts/screenshot.py http://localhost:8080/<url> --width 1440`, `--width 375`, светлая и тёмная (`--dark`) → `.tmp/screens/<page>-{light,dark}-{1440,375}.png`.
2. Длинный контент: страница с seed-записью в 80 символов и карточкой `dead`; `/topic/accessibility/` — empty-state; `/404-test/` — 404. Ничего не выезжает за 375 px по горизонтали.
3. Сверка с wireframe: каждая секция wireframe присутствует в том же порядке; отличия — только принятые в фазе 1.3.
4. `grep -rnE "#[0-9a-fA-F]{3,6}\b|[0-9]+px" wordpress/wp-content/themes/designstack/templates` — пусто; `python scripts/check_tokens.py` — ок; `debug.log` чист.
5. **Проверка глазами.** Ноль замечаний автоматики не значит, что страница хорошая. Пройти «Чеклист страницы» из карты вручную на каждом скриншоте: читаются ли подписи, не слиплись ли группы, видно ли, что кликается, а что просто написано, что происходит с длинным текстом и пустым списком. Найденное дописать в чеклист.
6. Апрув заказчика: показ партии — «было и стало» (скриншот до и после) и список изменений, а не список файлов; 4 скриншота на страницу (в bulk — по 2, остальные по запросу), `AskUserQuestion` «Страницу принимаем?» (Да / Правки: …). После «да» — статус `verified` в `_index.md`.

## Грабли

- **Агент норовит оживить.** Самая частая ошибка: «раз есть seed — подключу фильтр по `$_GET`». Нет: 14 делает это по спецификации, иначе следующий этап останется без работы, а логика — без состояний.
- **Wireframe ≠ финал.** Переложить серые прямоугольники 1:1 — значит получить такую же сырую страницу. Фаза 1.3 обязательна.
- **Мета одной строкой** «Free · EN · работает из РФ» — бейджи с иконками; иначе не сканируется и не проходит «статус не только цветом».
- **Плоские карточки.** Без `shadow-sm`/`border-default` карточки сливаются с фоном, особенно в тёмной теме. Тени — в первом проходе.
- **`core/query` и `resource`.** В `queryId` разные значения на странице; `postType: "resource"` и `taxQuery` задавать явно, иначе блок покажет записи `post`.
- **Шаблон не применяется.** Иерархия: `page-about.html` работает только при slug `about`; для таксономий — `taxonomy-resource_type.html`, не `archive-resource_type.html`. Проверять `curl`, а не верить имени файла.
- **Кэш шаблонов.** После правки `templates/*.html` — обновить страницу с `?nocache=1`; если редактор сайта сохранил свою копию шаблона в БД, файл игнорируется: `tools/wp.cmd --path=wordpress post list --post_type=wp_template` и удалить копию.
- **Локальная композиция как паттерн-призрак** в карте: если названа `designstack/<slug>`, файл обязан существовать. Иначе писать «локальная композиция».
- **375 px.** Сетка 3 → 1, панель фильтров → чипсы, шапка → `<details>`; горизонтальный скролл страницы — баг.
- **Список файлов в ответе заказчику.** «Обновил шесть шаблонов» ничего не показывает: нужны «было и стало» и список изменений на странице.
- **Bulk пересобирает готовое** — сверяться с `_index.md`; пересборка только по явному «да».

## Правила

- Никакой разметки до апрува composition map и до апрува решений с листа в чате; правки — сначала в карте.
- Пришли правки по составу после сборки — страница возвращается на лист решений, а не правится на месте.
- Страница — композиция из базы; паттерны и токены при сборке страниц не перерисовываются.
- Только пресеты и семантические токены в атрибутах блоков; hex/px в шаблонах запрещены.
- Правило 3+/2/1 применяется в каждом прогоне; вынос — через мини-цикл 11 с записью в каталог.
- Состояния обязательны: пусто / переполнение / dead / 404 описаны и проверены на реальных URL.
- Статика: ни логики, ни чтения параметров, ни рабочих форм. Данные seed через блоки — можно, поведение — нет.
- Индекс `_index.md` и `Used in` обновляются в том же прогоне, не «потом».
- Проверка по факту: `curl`, `debug.log`, ошибки темы, скриншоты 1440/375 в обеих темах, апрув заказчика.
