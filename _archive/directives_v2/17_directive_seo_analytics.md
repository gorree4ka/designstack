# Директива 17: SEO, Яндекс Метрика, гипотезы и итерации

Вход: `docs/spec.md`, `docs/ia/sitemap.md`, шаблоны темы и плагин `designstack-core`, `docs/brief.md` §4 (JTBD), §7 (SEO/аналитика), §9 (кластеры), §10 (OKR), `docs/brand/brand-direction.md`. Выход: `docs/analytics/seo-map.md`, `docs/analytics/goals.md`, `docs/analytics/rounds/<date>.md`, SEO- и трекинг-код в `plugins/designstack-core/`. Запуск: `/directive 17`

## Задача

Сделать сайт находимым и измеримым: SEO-разметка (title/description, canonical, `noindex`, schema.org, Open Graph, sitemap, robots), счётчик Яндекс Метрики с целями по ключевым действиям, составные цели-воронки по JTBD 1–6 и сегменты по типу ресурса. Из сценариев и целей вывести гипотезы с измеримыми порогами и вести ритуал раундов: снимок метрик → находки → задание → правки → передеплой → ретест. Верхнеуровневые пороги — OKR из brief §10.

## Когда применять

Первый раз — после сборки страниц (13) и оживления (14), до репозитория (18) и деплоя (19): разметка и трекинг должны уехать на хостинг вместе с темой и плагином. Повторно — после каждой итерации страниц, после деплоя (регистрация в Вебмастере и Search Console, проверка хитов), затем еженедельно как раунд метрик. Повторный запуск читает `docs/analytics/*` и обновляет, а не пересоздаёт.

- Сервер запущен: `curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/` → 200.
- Для фаз 6 и 8 — доступ заказчика к аккаунту Яндекса (браузерные шаги делает заказчик).

## Роль

SEO-специалист контентных каталогов + продуктовый аналитик. Ты знаешь, как Яндекс и Google обходят фасетные фильтры, зачем каталогу `ItemList`, чем составная цель Метрики отличается от событийной, и умеешь превратить «хочу больше трафика» в гипотезу с порогом и датой проверки.

## Ключевой принцип

**Измеряем работу пользователя, а не хиты.** Каждая цель Метрики — шаг одного из JTBD-сценариев; каждая гипотеза — сценарий + метрика + порог; каждый раунд заканчивается заданием на правку, а не отчётом. В SEO — **одна страница под один кластер запросов**: фильтры не плодят дубли, служебные страницы не индексируются, разметка описывает то, что есть в карточке, а не то, что хочется поисковику.

## Граница

Директива НЕ деплоит (это `19`), НЕ создаёт и не правит контент записей (это `16`), НЕ меняет дизайн-токены и паттерны (10, 11). Правки в теме и плагине — только для разметки, трекинга и настроек SEO. Цели и сегменты в интерфейсе Метрики создаёт заказчик по таблице из `goals.md` — у агента нет доступа к кабинету.

2. Снять инвентарь того, что уже есть в коде: `grep -rn "ld+json\|og:\|ym(\|data-track\|wp_robots\|canonical" wordpress/wp-content/themes/designstack wordpress/wp-content/plugins/designstack-core`. Всё найденное — в таблицу «есть / нет / переделать» в `.tmp/seo-inventory.md`.
3. Типы страниц для шаблонов (из sitemap): главная; архивы `/tools/`, `/learn/`, `/assets/`, `/community/`; архив с фильтрами; карточка `/resource/{slug}/`; тема `/topic/{slug}/`; подборка, дайджест, обзор (`post` по категориям); `/about/`, `/suggest/`, поиск, 404, `/styleguide/`.

### Фаза 1. Выбор SEO-плагина — апрув

`AskUserQuestion`, один вопрос, три варианта:
- **Yoast SEO (Recommended).** Бесплатной версии хватает: шаблоны title/description по типам записей и таксономиям, canonical, `sitemap_index.xml`, OG/Twitter, хлебные крошки, `noindex` для таксономий; есть WP-CLI-команды (`wp yoast index`). Схему Yoast для `resource` отключаем фильтром `wpseo_schema_graph_pieces`, чтобы не дублировать наш JSON-LD.
- **Rank Math.** Больше schema-типов в интерфейсе и гибче настройка индексации, но агрессивный upsell и телеметрия; выбирать, если заказчик хочет править разметку из админки без кода.
- **Без плагина.** Штатный `wp-sitemap.xml`, а title/description/canonical/OG — в `designstack-core`. Меньше зависимостей, но каждую SEO-мелочь пишем и поддерживаем сами.

Решение и обоснование — в `docs/analytics/seo-map.md` (раздел «Инструменты»). Установка: `tools/wp.cmd --path=wordpress plugin install wordpress-seo --activate`. Настройки плагина — через `wp option` и `wp yoast`, не руками в админке.

### Фаза 2. SEO-карта: кластеры → страницы — апрув

1. Кластеры из brief §9 разложить по страницам: каждая подборка — под один кластер, каждый архив — под общий запрос типа, каждая карточка — под «{название} обзор / аналоги», страницы `/topic/{slug}/` — под тематические запросы. Таблица в `docs/analytics/seo-map.md`: кластер | целевой запрос | страница | тип шаблона | title-шаблон | description-шаблон | статус (есть/нужен контент → `16`).
2. Шаблоны title/description по типам страниц (переменные плагина или `document_title_parts`): карточка — `{название} — {вердикт} | {бренд}`, description — `{review}` до 160 символов; архив — `{Тип}: {N} проверенных ресурсов для дизайнеров`; фильтр по одному фактору — `{Тип} {значение фильтра}`; подборка — заголовок записи как есть.
3. Правила индексации фильтров (brief §7): архив без фильтров и фильтр по **одному** фактору — индексируются, canonical на себя; **два и более факторов** — canonical на архив без фильтров + `noindex,follow`; **пустой результат** — `noindex`; `/styleguide/`, `/search/`, `/?s=`, страницы пагинации выше 1 — `noindex,follow`. Реализация — фильтр `wp_robots` и `get_canonical_url` в `designstack-core/includes/seo.php`, потому что правила зависят от query vars фильтров (14).
4. `AskUserQuestion`: подтвердить карту и правила индексации (≤3 вопроса: спорные кластеры, глубина индексации фильтров, нужен ли `noindex` для `/digest/` старше года).

### Фаза 3. Schema.org JSON-LD

В `designstack-core/includes/schema.php`, вывод в `wp_head`, один `<script type="application/ld+json">` с `@graph`:
- `resource` типа `tool` → `SoftwareApplication` (`name`, `url`, `applicationCategory`, `operatingSystem` из `platforms`, `offers` из `pricing`/`price_note`, `inLanguage`).
- `learning` → `Course` (для `format=course`), `Book` (`book`), иначе `CreativeWork`; `level`, `duration`, `provider`.
- `asset` → `CreativeWork` с `license`; `community` → `Organization`/`WebSite` с `sameAs`.
- Подборка → `CollectionPage` + `ItemList` из карточек блока «список ресурсов»; архивы → `CollectionPage` + `ItemList` первой страницы.
- `BreadcrumbList` на всех внутренних страницах (из тех же данных, что и хлебные крошки темы).
- Отключить дублирующие сущности плагина на `resource`/архивах (Yoast — `wpseo_schema_graph_pieces`).

Проверка: `curl -s http://localhost:8080/resource/<slug>/ | python -c "import sys,re,json; [json.loads(m) for m in re.findall(r'<script type=\"application/ld\+json\">(.*?)</script>', sys.stdin.read(), re.S)]; print('ok')"` на каждом типе страницы + `debug.log` чист. Внешняя валидация (validator.schema.org, Rich Results Test, Вебмастер → «Проверка микроразметки») — после деплоя, ссылки в отчёт.

### Фаза 4. Open Graph и OG-изображения

1. `og:title`, `og:description`, `og:url` (canonical), `og:type` (`website` / `article`), `og:image` + `og:image:width/height`, `twitter:card=summary_large_image`, `og:locale=ru_RU`. Telegram и vc.ru берут превью из OG — это канал дистрибуции из brief §9, не формальность.
2. Изображения по правилам `docs/brand/brand-direction.md`: 1200×630, WebP/PNG, набор по умолчанию в `themes/designstack/assets/og/`: `default`, `tool`, `learning`, `asset`, `community`, `collection`, `digest`. Карточка ресурса → изображение типа (логотипы вендоров в OG не ставим, brief A9). Генерация карточек «на лету» — не в MVP, записать в допущения.
3. Проверка: `curl -s <url> | grep -o '<meta property="og:[^>]*>'` на всех типах; изображения отдаются с 200.

### Фаза 5. sitemap.xml, robots.txt, видимость

1. Sitemap: плагин (`/sitemap_index.xml`) или штатный `/wp-sitemap.xml`; исключить `/styleguide/`, страницы с `noindex`, медиа-вложения. Записи со `status=dead` остаются (не удаляем, brief §5) — но с пометкой в карточке, не в sitemap-исключениях.
2. `robots.txt` через фильтр `robots_txt` в плагине: `Disallow: /wp-admin/`, `/search/`, `/*?s=`, `/styleguide/`, параметры многофакторных фильтров; `Sitemap: https://<domain>/sitemap_index.xml`; для Яндекса — `Clean-param` на UTM-параметры и `ut_task`.
3. Убедиться, что на продакшене `blog_public=1` (`wp option get blog_public`); локально значение неважно.
4. Регистрация в Яндекс Вебмастере и Google Search Console — **после деплоя (19)**, браузерные шаги заказчика: добавить сайт, подтвердить через мета-тег (значение — в опцию плагина `designstack_verification_*`, выводится в `wp_head`) или DNS, отправить sitemap, в Вебмастере включить «Быстрые ссылки» и проверить регион. Результат — в `PROJECT.md` (без токенов).

### Фаза 6. Яндекс Метрика — апрув

1. Счётчик создаёт заказчик (metrika.yandex.ru → Добавить счётчик → домен из `naming.md`, часовой пояс Москва, **вебвизор выключен**, карта кликов включена). Присылает **ID счётчика** — это не секрет, пишется в `PROJECT.md`.
2. В плагине: страница настроек «DesignStack» (`options.php`, `register_setting`), опция `designstack_metrika_id`; вывод кода счётчика в `wp_head` **только** при `wp_get_environment_type() === 'production'` и непустом ID, параметры `webvisor:false, clickmap:true, trackLinks:true, accurateTrackBounce:true, ecommerce:false`. Вне продакшена — заглушка `window.ym = (...a) => console.debug('ym', ...a)`, чтобы события были видны в консоли и `track.js` не падал.
3. Разметка действий атрибутами `data-track="<goal>"` (+ `data-track-type`, `data-track-value`) в паттернах/блоках; `designstack-core/assets/js/track.js` (без зависимостей, ≤100 строк) делегирует клики и `submit`, вызывает `ym(id,'reachGoal',goal,{resource_type, value})`. Цели:

| Цель | Где срабатывает | Параметры |
|---|---|---|
| `resource_outbound` | клик по внешней ссылке ресурса в карточке и списке | `resource_type`, `slug`, `ru_open`, `ru_payment` |
| `filter_apply` | применение фильтра в архиве | `resource_type`, `filter`, `value` |
| `subscribe` | успешная подписка на дайджест | `source` (footer / главная / дайджест) |
| `suggest_submit` | успешная отправка формы «предложить» | — |
| `theme_toggle` | переключение темы | `to` (light / dark) |
| `search_empty` | поиск без результатов (выстреливает шаблон пустого состояния) | `query_length` |
| `ru_alternative_click` | переход на карточку аналога из блока «работает из России» | `resource_type` |

4. Сегменты: на каждой странице `resource` — `ym(id,'params',{resource_type, ru_open, ru_payment, pricing})`; на архивах — `{resource_type}`. Также `ym(id,'userParams')` не используем (нет аккаунтов).
5. Составные цели по JTBD 1–6 (создаёт заказчик в интерфейсе, шаги в таблице `goals.md`): JTBD 1 — главная → `/learn/` или `/tools/` → `filter_apply` (level=junior) → `resource_outbound`; JTBD 2 — архив → `filter_apply` → карточка → `resource_outbound`; JTBD 3 — поиск/тема → карточка с `ru_open≠open` или `ru_payment=no_payment` → `ru_alternative_click`; JTBD 4 — `/assets/` → `filter_apply` (license/cyrillic) → `resource_outbound`; JTBD 5 — любая → `subscribe`; JTBD 6 — `/suggest/` → `suggest_submit`.
6. `AskUserQuestion`: подтвердить список целей и воронок, спросить про исключение своего IP из статистики (рекомендуется фильтр в настройках счётчика) и хотят ли ежедневный e-mail-отчёт Метрики.
7. Проверка локально: `curl` карточки содержит `data-track="resource_outbound"` и заглушку; `python scripts/screenshot.py` не падает; `debug.log` чист. Реальные хиты проверяются после деплоя (чеклист `19` → «Метрика получает хиты»).

### Фаза 7. Сценарии, гипотезы, пороги → `goals.md` — апрув

Формат сценария (по одному на JTBD 1–6, id латиницей):
```yaml
- id: tool-by-task            # JTBD 2
  funnel: [/tools/, /tools/?topic=prototyping, /resource/<slug>/]   # страницы по порядку
  goal: resource_outbound       # целевое действие (= успех)
  firstClick: { from: /, expect: "nav → Инструменты" }
```
Формат гипотезы: `id`, `text`, `flow` (id сценария), `measure` — `completion` (доля дошедших до `goal`, отчёт по составной цели) / `firstclick` (доля верных первых кликов: карта ссылок или цель `first_click` с параметром `target` из `track.js`) / `dropoff` (отвал перед шагом `step`, конверсия шага составной цели) / `lostness` (потерянность: `1 − оптимальная длина пути / фактическая глубина просмотра` в сегменте сценария), `target: {op: ">=" | "<=", value}`, `step` только для `dropoff`, `status`. Гипотеза без `flow`/`measure`/`target` — не гипотеза, а пожелание; в файл попадает в раздел «Без порога».

Пороги-ориентиры для старта: completion ≥ 0,4 для JTBD 2, dropoff на фильтрах ≤ 0,3, firstclick ≥ 0,6, lostness ≤ 0,4; верхний уровень — OKR brief §10 (1 000 визитов/мес через 3 месяца, 25 % возвращающихся через 12). Ссылка для юзер-теста по сценарию: `https://<domain><funnel[0]>?ut_task=<id>` — `track.js` читает `ut_task`, шлёт `ym(id,'params',{ut_task})` и дописывает `utm_source=ut&utm_campaign=<id>`, чтобы сегмент строился штатными отчётами по UTM. `AskUserQuestion`: пороги и приоритет гипотез (≤3 вопроса).

### Фаза 8. Ритуал раунда → `rounds/<date>.md`

1. **Снимок.** Данные из Метрики за период: заказчик выгружает отчёты (составные цели, конверсии, источники, сегменты по `resource_type`) в CSV в `.tmp/metrika/`, либо агент читает API `curl -H "Authorization: OAuth <token>" "https://api-metrika.yandex.net/stat/v1/data?ids=<id>&metrics=ym:s:visits,ym:s:goal<goal_id>conversionRate&..."` — токен только в команде, не в файлах. Плюс Вебмастер/Search Console: запросы, показы, позиции по кластерам из `seo-map.md`.
2. **Было / стало** по всем сценариям и гипотезам: таблица `гипотеза | measure | порог | прошлый раунд | сейчас | вердикт (подтверждена / опровергнута / мало данных)`. Мало данных = меньше 30 сессий в сегменте — вердикт не выносим.
3. **Находки:** 3–7 штук, каждая с данными, страницей и предполагаемой причиной (отвал на фильтрах, пустой поиск по частым запросам, низкий CTR карточек в выдаче).
4. **Задания:** каждая находка → директива-исполнитель (`13` шаблон, `14` поведение, `16` контент, `11` паттерн) + критерий проверки в следующем раунде. Задания выводятся заказчику списком на апрув.
5. После правок → `18` (коммит) → `19` (передеплой) → ретест (юзер-тест по ссылке `?ut_task=`) → следующий раунд. Еженедельный ритм совпадает с дайджестом; напоминание — в `PROJECT.md` (дата следующего раунда).

```
- Метрика: счётчик <ID> (только production, вебвизор выкл.), целей: 7, составных: 6 (JTBD 1–6), сегменты по resource_type
- Сценарии: <N> · гипотезы с порогами: <N> · ссылки для юзер-тестов в goals.md
- Раунд: docs/analytics/rounds/<дата>.md — находок <N>, заданий <N> (→ 13/14/16)
Следующий шаг: <18 репозиторий → 19 деплой | заказчик: цели и воронки в интерфейсе Метрики, регистрация в Вебмастере/GSC | правки по заданиям → передеплой → ретест>
```

## Грабли

- **Схема плагина дублирует нашу.** Yoast/Rank Math выводят свой `@graph` (`WebPage`, `Article`); два `SoftwareApplication` на странице — ошибка валидатора. Отключать чужие куски фильтром, оставлять один граф.
- **Фасетные фильтры съедают краулинговый бюджет.** Каждая комбинация — отдельный URL; без canonical + `noindex` поисковик индексирует тысячи дублей. Правило «один фактор индексируем, два и больше — нет» реализовать в коде, а не в настройках плагина.
- **Счётчик на локалке и на staging.** Хиты разработчика ломают статистику. Только `production` по `WP_ENVIRONMENT_TYPE`, плюс фильтр своего IP в настройках счётчика.
- **Свои проверки считаются визитами.** Частый `curl` живого сайта, скрипт проверки ссылок (16) и мониторинг хостинга попадают в Метрику и могут разбудить анти-DDoS хостинга. Проверки — редко, с узнаваемым `User-Agent`, IP исключён; Метрика на серверный `curl` не реагирует, а вот Playwright-скриншоты — да.
- **Цели «на время сессии».** Снимок метрик, сделанный «когда вспомнил», несравним между раундами. Раунд — по расписанию (еженедельно, вместе с дайджестом); еженедельная выгрузка и проверка ссылок — cron хостинга (`wp cron event run --due-now` по крону, не WP-Cron от посетителей).
- **Два сценария с одной стартовой страницы.** Сессии смешаются; юзер-тесты только по ссылке с `?ut_task=<id>`, иначе не привязать.
- **OG-превью закешировано.** Telegram и vc.ru кешируют первую версию; после смены изображения — сбросить через `t.me/WebpageBot` и обновить `og:image` URL версией.
- **`blog_public=0` на продакшене.** Сайт после переноса может приехать с галкой «не индексировать» — проверить `wp option get blog_public` в чеклисте 19.
- **Гипотеза без порога** — не проверяема; «стало лучше» без числа в `rounds/` не принимается.

## Правила

- Одна страница — один кластер; фильтры не плодят индексируемые дубли.
- Разметка и трекинг живут в `designstack-core` (данные не зависят от темы); тема только расставляет `data-track` в паттернах.
- Цели именуются латиницей в snake_case, одинаково в коде, `goals.md` и Метрике.
- Вебвизор выключен; персональные данные и ввод форм не трекаются.
- Токены API Метрики транзиентны — только в команде; ID счётчика — публичный, в `PROJECT.md`.
- Гипотеза = сценарий + measure + порог; вердикт — только при достаточной выборке.
- Повторный запуск обновляет `seo-map.md`/`goals.md` и добавляет новый файл в `rounds/`, старые раунды не переписываются.
