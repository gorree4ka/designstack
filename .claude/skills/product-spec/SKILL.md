# Этап 06 · Функции, приоритеты, ТЗ

> До 15.09.2026 это была директива `06_directive_spec.md`; исходник — `_archive/directives_v2/`.
> Этап 06 конвейера (00_pipeline.md). Вход: `docs/brief.md`, `docs/research/competitive_analysis.md`, `docs/personas.md`, при наличии `docs/interviews/*.md`. Выход: `docs/features.md`, `docs/spec.md`. Запуск: `/product-spec`

## Задача

Собрать из брифа, конкурентного анализа, персон и интервью полный список функций с источниками, приоритизировать по MoSCoW, согласовать scope MVP с брифом §11 и написать ТЗ `docs/spec.md` с user stories и проверяемыми критериями приёмки. `docs/spec.md` становится источником критериев приёмки для 13 (шаблоны), 14 (поведение) и 15 (аудит): чего там не записано — проверять будет не по чему.

## Когда применять

- После 03–04 (05 опц.), перед 07. Повторно — при изменении брифа через 02, после итогов интервью, после аудита 15 или данных 17. Повторный запуск — синхронизация: ID сохраняются, версия ТЗ +0.1, изменения датируются.

## Предусловие

- `docs/brief.md` ≥ 1.0 утверждён. Нет — `/briefing`.
- `docs/research/competitive_analysis.md` — нужен для table stakes и дифференциаторов. Нет — `/competitor-research` (допустимо продолжить по `competitors.md` с пометкой в шапке ТЗ).
- `docs/personas.md` — нужен для колонки «Персона» и user stories. Нет — `/personas`.
- `docs/interviews/*.md` — опционально; используются с пометкой «синтетическое».

## Роль

Product Manager + Senior Product Designer с опытом ТЗ для WordPress-каталогов. Пишешь для трёх читателей: заказчик (понять и утвердить), агент-разработчик в 12–14 (собрать без домыслов), аудитор в 15 (проверить по чеклисту). Критерий приёмки, который нельзя проверить `curl`-ом, скриншотом или глазами за минуту, — не критерий.

## Ключевой принцип

Функция без источника и персоны в список не попадает. Must — только то, без чего primary-персона (`junior-switcher`) не выполнит JTBD №1–№2 или не выполняется одно из трёх обещаний. ТЗ уточняет бриф, а не спорит с ним: расхождение с §11 — вопрос заказчику, не тихая правка.

## Граница

Не проектирует URL и шаблоны (07), не рисует wireframes (08), не выбирает название и палитру (09–10), не пишет код (12–14). Не меняет `docs/brief.md`.

### Фаза 2. MoSCoW

Каждой функции — категория и обоснование одной строкой:
- **Must** — выполняются все три критерия: (1) прямо связана с JTBD primary-персоны №1–№2 или с одним из трёх обещаний; (2) без неё основной сценарий «главная → архив с фильтром → карточка → переход на ресурс» невозможен или обещание не выполняется; (3) либо table stakes по CA (есть у ≥ 3 конкурентов), либо дифференциатор, ради которого нас выберут.
- **Should** — важно, запуститься можно без; первая итерация после запуска (v1.1).
- **Could** — полезно; при наличии ресурса (v2.0).
- **Won't (now)** — осознанно откладываем; причина записана.

Сверить с брифом §11: всё из «В MVP» должно быть Must или Should с обоснованием; всё из «Не в MVP» — Could или Won't. Расхождения — список для фазы 3. Апрув (`AskUserQuestion`, до 3 вопросов) по спорным Must/Should с рекомендацией: например, «похожие» на карточке (Recommended: Should), сортировка архива (Recommended: Should — по дате проверки), страница темы `/topic/` (Recommended: Must — вход из SEO), RSS дайджеста (Recommended: Could).

### Фаза 3. Scope MVP

1. **Одно предложение** — что это за продукт в MVP.
2. **Список Must** с ID.
3. **Основной сценарий** primary-персоны от входа до результата шагами «страница → действие → результат»; плюс два коротких: П2 — аналог закрытого сервиса (JTBD №3), П3 — поделиться подборкой.
4. **Что осознанно не входит** — топ-3 Should с причиной «почему не сейчас».
5. Если scope расходится с §11 (функция из «В MVP» попала в Should, или Must требует того, чего в §11 нет) — `AskUserQuestion`: «оставить как в брифе (Recommended)» / «изменить scope — заказчик инициирует правку брифа через 02» / свободный текст. Без апрува бриф главнее.

### Фаза 4. ТЗ → `docs/spec.md`

Разделы H2 в этом порядке:

1. **Executive summary** — продукт одним предложением; проблема (brief §1, дыры 5–6 из `competitors.md`); ключевой инсайт из CA; решение (scope MVP); primary-персона и её JTBD.
2. **Цели и метрики** — из brief §10 (запуск / 3 месяца / 12 месяцев) как 2–3 OKR с Key Results; North Star — рекомендация: переходы по ссылкам ресурсов в неделю (цель Метрики из §7); перечень событий, которые 17 заведёт как цели.
3. **Аудитория** — три персоны по 3–4 предложения, приоритет, JTBD, ссылка на `docs/personas.md`.
4. **Конкурентный ландшафт** — 5–7 предложений и таблица дифференциаторов из CA; ссылка на `competitive_analysis.md`, матрицу не копировать.
5. **MVP scope** — из фазы 3.
6. **User stories** — для каждой Must-функции: `US-NN` (→ `F-NN`), «Как [персона], я хочу [действие], чтобы [результат]», приоритет, 3–7 критериев приёмки в форме «Дано / Когда / Тогда» или проверяемого утверждения с числом, URL или состоянием. Обязательно покрыть:
   - **фильтры архивов** — оси по типу из §6; множественный выбор; отражение в URL; сброс; счётчик результатов; пустая выдача с подсказкой и ссылкой на «предложить ресурс»; `noindex` пустых комбинаций; мобильный вариант (чипсы + панель);
   - **карточка ресурса** — все поля §5.1 и §8; условные поля по типу; аналоги `ru_alternative`; «похожие»; schema.org по типу; кнопка перехода с целью Метрики;
   - **доступ из РФ** — два поля D15: по три значения `ru_open` и `ru_payment`, каждое как иконка + текст, не только цвет; у бесплатных ресурсов бейджа оплаты нет (D28); ссылка на аналог; статусы `changed` / `dead` с плашкой и предложением аналога; фильтр по статусу;
   - **дата проверки** — формат «проверено 3 сен 2026»; предупреждение при `checked_at` старше 90 дней; сортировка по дате проверки;
   - **подборки** — блок «список ресурсов» по ID или тегам; карточки живые (статус и дата подтягиваются из записи); `ItemList`; страница и архив;
   - **дайджест** — страница и архив; автосборка черновика за неделю по `checked_at`/`date`; форма подписки; кнопка Telegram;
   - **форма «предложить ресурс»** — поля; nonce, honeypot, лимит по IP; состояния по умолчанию / ошибки полей / отправка / успех / ошибка отправки; письмо куратору; черновик в очереди;
   - **поиск** — по названию, вердикту, оценке; подсветка типа в выдаче; пустая выдача с подсказкой;
   - **темы** — `/topic/{slug}/` со всеми типами и фильтром по типу; иерархия тем;
   - **тёмная тема** — переключатель в шапке; системная по умолчанию; запоминание выбора; контраст ≥ 4,5:1; без вспышки при загрузке.

   Пример критерия: «Дано: архив `/tools/` с `?ru_payment=payable&pricing=freemium`. Когда: страницу открывают по этой ссылке. Тогда: оба фильтра показаны активными чипсами, счётчик показывает число записей, `<link rel="canonical">` указывает на этот же URL, `curl` возвращает 200».
7. **Нефункциональные требования** — каждое с порогом и способом проверки (Lighthouse, `curl`, WP-CLI, скриншот): Core Web Vitals (LCP < 2,5 с, CLS < 0,1, INP < 200 мс на 375 и 1440 px); WCAG 2.2 AA (контраст, клавиатура, видимый фокус, `prefers-reduced-motion`, статусы не только цветом, alt у логотипов); SEO (ЧПУ, schema.org по типам, Open Graph, sitemap, канонические для фильтров, `noindex` пустых); безопасность (`DISALLOW_FILE_EDIT`, nonce, honeypot, лимиты, 2FA куратора, ПД только в форме подписки с согласием); производительность запросов (архив с фильтрами — фиксированное число запросов к БД, без N+1 в блоке «список ресурсов», кеш страниц); отсутствие аккаунтов (все публичные функции без входа; роли — только редакция); совместимость (MySQL 8 и SQLite, WordPress 7.x, PHP 8.3); адаптив 600 / 900 / 1200; русская типографика §8.
8. **Риски и открытые вопросы** — threats из SWOT; противоречия из интервью; допущения брифа §12 с датой пересмотра; вопросы для реального кастдева.
9. **Roadmap** — таблица: v1.0 (MVP) = Must; v1.1 = Should; v2.0 = Could (+ H2 / H5 / H6 из §11 как кандидаты); Won't — отдельно с причиной.
10. **Трассировка** — таблица `F-NN → US-NN → страница §6 → кто проверяет (13 / 14 / 15)`.

## Грабли

- Список функций — копия §11. Бриф даёт крупные блоки; функции — проверяемые единицы («фильтр по цене в URL», а не «фильтры»).
- Всё Must. Если Must больше 60 % списка — критерии не применялись; повторить фазу 2.
- Критерии «удобно», «быстро», «понятно». Заменять числом или наблюдаемым фактом.
- User story на 20 критериев — это несколько функций; разбить.
- NFR «как в брифе» без порогов — в 15 нечего проверять.
- Тихая правка scope относительно §11. Только через вопрос заказчику.
- ТЗ переписано с нуля при повторном запуске — теряются ID и ссылки из 13–15. Только синхронизация.
- Забытые операционные функции (проверка ссылок, очередь перепроверки, автосборка дайджеста): они в §5.3, без них обещание «актуальность» не выполняется.

## Правила

- Русский язык; названия продуктов, поля (`ru_open`, `ru_payment`), ID (`F-NN`, `US-NN`) — латиницей.
- Апрув — `AskUserQuestion`, ≤ 3–4 вопроса за раз, с рекомендацией; «решай сам» — допущение в шапке ТЗ.
- Бриф главнее ТЗ; ТЗ главнее всех документов ниже по конвейеру.
- Повторный запуск — синхронизация: ID сохраняются, новые функции получают следующие номера, удалённые помечаются «отменено <дата>», версия +0.1.
- Публикация через `Artifact` — только по запросу заказчика.
