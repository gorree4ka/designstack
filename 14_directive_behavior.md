> Этап 14 конвейера (00_pipeline.md). Вход: шаблоны из 13 (`templates/*.html`, `docs/ds/screens/*.md`), плагин из 12, `docs/spec.md`, `docs/ia/flows/*.mmd`. Выход: рабочие навигация, фильтры, сортировка, поиск, пагинация, формы; секция `## Edge cases` в `docs/ds/screens/<page>.md`; статус «оживлено» в `docs/ds/screens/_index.md`. Запуск: `/directive 14`

## Задача

Превратить собранные в 13 статичные страницы в рабочий сайт: навигация ведёт куда надо, архивы фильтруются и сортируются по URL, поиск находит по вердикту и оценке, форма «предложить ресурс» принимает и валидирует, каждый список и каждая форма показывают не только «когда всё хорошо», но и пусто / ошибку / переполнение. Данные — реальные записи `resource` из `scripts/seed.py` (12): никакого мок-слоя, сайт работает на том же коде, что пойдёт на хостинг.

## Когда применять

- После 13: шаблоны собраны, `_index.md` показывает статус «собрано», но фильтры — декорация, форма никуда не отправляет.
- **Повторно и многократно:** оживить ещё страницу, добавить поведение по запросу заказчика, доанимировать. Каждый запуск наращивает, существующее не ломает.

## Предусловие

- `docs/spec.md` с критериями приёмки (06), `docs/ia/flows/*.mmd` (07), `docs/ds/screens/_index.md` и `docs/ds/screens/<page>.md` (13), `docs/ds/components.md` (11) — в нём паттерны состояний: пустое состояние, сообщение об ошибке, плашка статуса, чипсы фильтров.
- Плагин `wordpress/wp-content/plugins/designstack-core/` активен, `scripts/seed.py` отработал: `tools/wp.cmd --path=wordpress post list --post_type=resource --format=count` ≥ 24 (столько создаёт seed из 12; реальный объём приходит на 16).
- Сервер запущен: `curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/` → 200. Нет чего-то — отправь в 12/13, не начинай.

## Роль

Senior WordPress-разработчик с продуктовым чутьём: знает `WP_Query`, `pre_get_posts`, `query_vars`, блочную тему, умеет сделать фильтры без JS и не тащит библиотеки. Логику формулирует заказчик, обработчики пишешь ты; заказчик в код не лезет.

## Ключевой принцип

Сайт становится живым за счёт четырёх вещей: **навигация** (меню, крошки, активный пункт), **выборка данных** (фильтры, сортировка, поиск, пагинация — серверные, через URL), **формы** (ввод → проверка → результат), **состояния по действию** (пусто / ошибка / успех / переполнение + edge-cases). Всё на паттернах из `components.md` и токенах `theme.json`. JS — только прогрессивное улучшение: без него всё работает.

5. Подвал: подписка (Фаза 3.4), Telegram, «Принципы оценки» (якорь на `/about/`), политика данных (страница-заглушка, текст — Q6 брифа).

### Фаза 2. Фильтры, сортировка, поиск, пагинация

Сначала проба, потом реализация: файл `.tmp/probes/pre-get-posts.php`, `pre_get_posts` с двумя-тремя фильтрами (`pricing`, `ru_payment`, `topic`) на архиве `resource`, `SAVEQUERIES` и подсчёт `$wpdb->queries`. Смотрим три вещи: выборка та, что ждали; админка и второстепенные запросы не задеты; число запросов известно цифрой. Результат — строкой в `docs/DECISIONS.md`, проба удаляется. Не проверил — значит не знаешь: `meta_query` на SQLite и хук главного запроса ломаются молча.

1. Query vars регистрируются в плагине (`query_vars`): общие `pricing`, `ru_open`, `ru_payment`, `topic`, `level`, `sort` (`ru_payment=payable` включает бесплатные ресурсы без поля оплаты, D28); по типу — `platform` (tool, community), `format` и `language` (learning), `license` и `cyrillic` (asset), `is_jobs` (community). Значения — только из enum brief §5.1; чужое значение игнорируется (не 404).
2. `pre_get_posts` только для главного запроса архивов `resource` и `/topic/{slug}/`: таксономии → `tax_query` (`topic`, `level`, `resource_type`), meta-поля → `meta_query` с `relation => AND`. Сортировка `sort=checked` (по `checked_at` desc, Recommended по умолчанию) / `title` / `new`. Мёртвые (`status=dead`) в архивах — в конец или скрыты: спроси.
3. URL фильтров индексируемые и шарящиеся: `/tools/?pricing=freemium&ru_payment=payable&topic=prototyping`. `rel="canonical"` при активных фильтрах — на чистый архив (`get_canonical_url`); `noindex` через `wp_robots` для пустых выдач и комбинаций из 3+ факторов. При появлении SEO-плагина в 17 — проверить, что теги не дублируются.
4. Панель фильтров (паттерн из 11, блок `designstack/filters` или `<form method="get">`): без JS работает по кнопке «Применить»; с JS — авто-submit при изменении с задержкой 250 ms. Над списком — чипсы активных фильтров (каждый снимается по ×) и «Сбросить всё» → чистый архив. Счётчик «Найдено: N». Счётчики у значений фильтров — через transients (Фаза 6).
5. Поиск: штатный `s=`, шаблон `templates/search.html`. Расширение: `posts_join` + `posts_search` + `posts_distinct` в плагине добавляют поиск по meta `verdict` и `review` (только для `resource` и `post`). На странице результатов — те же чипсы типов (`resource_type`) для сужения.
6. Пагинация: блок `query-pagination`; проверь, что ссылки страниц сохраняют query string фильтров и что `/tools/page/2/?pricing=free` отдаёт 200. Несуществующая страница пагинации, неизвестный term, неизвестный slug → штатный 404 и `templates/404.html`.
7. `AskUserQuestion` (≤3): сортировка по умолчанию; показывать ли `dead` в архивах; мобильные фильтры — выезжающая панель (Recommended, brief §8) или блок под заголовком.

### Фаза 3. Формы

1. `designstack/suggest-form` (блок из 12, страница `/suggest/`). Поля: URL (обязательно, `wp_http_validate_url`), название (≤120), тип (enum из 4), комментарий «почему стоит добавить» (≤1000), email (необязательно, `is_email`). Защита: nonce, honeypot (скрытое поле должно остаться пустым), лимит по IP через transient (3 отправки в час, Recommended). Дубль: URL уже есть среди `resource` любого статуса → сообщение «Уже в каталоге: <ссылка>» без создания записи.
2. Обработка через `admin_post_nopriv_designstack_suggest` / `admin_post_designstack_suggest`; без JS форма отправляется обычным POST. Ошибки — по полям, с сохранением введённого (`aria-describedby`, `aria-invalid`, текст ошибки говорит, что исправить). Успех — по схеме PRG: редирект на `/suggest/?sent=1` с inline-сообщением (Recommended) либо страница «Спасибо» — спроси.
3. При успехе: запись `resource` со статусом `pending`, заполнены `url`, `resource_type`, черновик названия; комментарий и email — в приватных meta для куратора; письмо куратору через `wp_mail` (локально письма не уходят — факт отправки логируется в `debug.log` пометкой `[designstack] suggest`).
4. Подписка на дайджест (brief §13 Q4, сервис не выбран): паттерн `subscribe-cta` берёт `action` из опции `designstack_newsletter_action`. Пока опция пуста — вместо полей выводится плашка «Дайджест выходит в Telegram: <ссылка>; рассылка скоро» (Recommended: не собирать email без сервиса и политики). Чекбокс согласия и ссылка на политику — в разметке заранее.
5. `AskUserQuestion` (≤3): лимит отправок; успех inline или отдельная страница; какие поля обязательны.

### Фаза 4. Состояния и edge-cases

Обязательная часть, не опция. По каждой странице из `_index.md` пройди матрицу и реализуй недостающее паттернами из `components.md`:

| Блок | Состояния |
|---|---|
| Список / архив / результаты поиска | с данными · пусто · загрузка (только при JS-фильтрах, иначе «н/п») · ошибка (битые meta, недоступный term) · переполнение (200+ записей, длинные названия и теги) |
| Форма | по умолчанию · валидные поля · ошибки полей · отправка (кнопка заблокирована, текст «Отправляем…») · успех · ошибка отправки (лимит, nonce, дубль) |
| Карточка ресурса | по умолчанию · нет логотипа (фолбэк — первая буква на нейтральном фоне) · длинное название (2 строки, обрезка) · `changed` (жёлтая плашка «условия изменились» + дата) · `dead` (плашка «закрыт, аналог: <ссылка на ru_alternative>», ссылка на ресурс без `href`) |
| Доступ | не применяется: аккаунтов нет (brief §7) — фиксируй как «н/п» |

- Тексты состояний — из `docs/VOICE.md`: пусто, ничего не найдено, ошибка, форма отправлена. Ошибка объясняет причину и следующий шаг («Ссылка не похожа на адрес — начни с https://»), а не сообщает факт («Ошибка»). Нового слова мимо словаря не появляется.
- Пустой архив: «По таким условиям ничего нет» + кнопка «Сбросить фильтры» + 3 ближайших темы.
- Поиск без результатов: подсказки — популярные темы, 4 типа, ссылка «Предложить ресурс». Запрос показывается в кавычках, HTML экранирован.
- Карточка без `ru_alternative` при `dead`: текст «аналог пока не подобран» + ссылка на форму.
- Предложи заказчику 3–5 дополнительных edge-cases по продукту (например, `checked_at` старше 90 дней → бейдж «Давно не проверяли» из `docs/VOICE.md`); `AskUserQuestion` (1 вопрос): какие добавить.
- Запиши результат в `docs/ds/screens/<page>.md` секцией `## Edge cases`: таблица «блок · состояние · реализовано (где) / н/п (почему) / отложено».

### Фаза 5. Переходы и движение

Раскрытие панели фильтров, появление чипсов, смена темы, фокус — переходы 150–200 мс через токены `--wp--custom--duration--fast|base` и `--wp--custom--ease--standard` из 10; нет нужного токена — мини-цикл 10 с записью в `foundation.md`, а не цифра в CSS. Всё под `@media (prefers-reduced-motion: reduce)` отключается. Никаких JS-анимационных библиотек. Опционально: заказчик может отложить движение на повторный запуск.

### Фаза 6. Производительность выборок

1. Считай запросы: `define( 'SAVEQUERIES', true )` локально и `tools/wp.cmd --path=wordpress eval` с подсчётом `$wpdb->queries` после `WP_Query` архива, либо Query Monitor (локально, не на хостинг). Цель: архив на 24 карточки ≤ 30 запросов, карточка ≤ 20.
2. Никакого N+1 в `resource-list` и карточках: meta и термины подтягиваются кешем `WP_Query` (`update_post_meta_cache`, `update_post_term_cache`), `ru_alternative` — одним `_prime_post_caches` по собранным ID.
3. Счётчики значений фильтров и списки терминов — в transients на 1 час, сброс на `save_post_resource`, `edited_term`, `delete_term`.
4. SQLite ≠ MySQL: не полагайся на порядок без `orderby`, `meta_query` с `type => DATE` проверь на обеих (MySQL — в 19).

## Грабли

- **Happy-path-only.** Оживили «когда всё хорошо», забыли пусто / ошибку / переполнение / `dead`. Фаза 4 обязательна, матрица закрывается целиком.
- **Фильтры только на JS.** Без JS форма фильтров должна отправляться и работать; JS — надстройка.
- **`pre_get_posts` ломает админку и другие запросы.** Проверяй `is_admin()`, `is_main_query()`, тип архива.
- **`meta_query` по каждой карточке = N+1.** Смотри счётчик запросов, а не «вроде быстро».
- **Прибитые значения в новых состояниях.** Плашки, пустые состояния, ошибки — из паттернов и токенов; 15 поймает.
- **Форма без защиты.** Nonce + honeypot + лимит по IP + проверка дубля — стандарт, не опция.
- **Утечка ввода.** Всё, что пришло из формы и `?s=`, экранируется при выводе (`esc_html`, `esc_attr`, `esc_url`).
- **SQLite прощает то, что MySQL не простит.** Не пиши SQL, только `WP_Query`; полный прогон на MySQL — в 19.
- **Повторный запуск ломает сделанное.** Наращиваем: читаем, что подключено, дописываем, дубликаты не плодим.

## Правила

- Логику формулирует заказчик, обработчики пишешь ты; очевидное из макета делаешь без вопросов, продуктовые решения — через `AskUserQuestion`.
- Данные реальные (seed), мок-слоя нет; серверный рендер, JS — прогрессивно.
- Edge-cases — стандарт; «н/п» допустимо только с причиной в `## Edge cases`.
- Тексты состояний — из `docs/VOICE.md`; ошибка называет причину и что делать дальше, а не факт поломки.
- Разбор идёт по классу: одна показанная ошибка = класс, правило со способом проверки в `docs/DECISIONS.md` и обход всех мест этого класса.
- Нетривиальную выборку сначала проверяем маленькой пробой в `.tmp/probes/` со счётчиком запросов, потом строим на ней логику.
- Только паттерны `components.md` и токены `theme.json`; код только в теме и `designstack-core`, по `.claude/rules/wp-theme.md`.
- Каждая правка проверяется по факту: `php -l` (хук), `curl`, `debug.log`, скриншот.
- Повторный запуск = наращивание: ещё страница, ещё поведение, движение.
